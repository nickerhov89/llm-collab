# Публикации через чат SEO & PR

Основной интерфейс — обычный чат коворка. Пример:

> Возьми две готовые статьи из media-desk, адаптируй под площадки и сохрани
> черновики в Workspace и Sostav. Верни ссылки, на модерацию не отправляй.

Агент выполняет работу сам через MCP `polza-media-browser` (резерв — CLI `polza-media`). Маркетологу не
нужно открывать панель, передавать куки, писать команды или составлять JSON.
Служебный экран браузера нужен только для ручного входа и проверки площадки.

## Инструкция агенту

1. Определи материалы и явно запрошенное действие: черновики, модерация или
   публикация. При неизвестной площадке используй актуальные MEDIA.md и план
   размещения. Не выдавай одну и ту же статью за уникальную адаптацию для всех СМИ.
2. Основной путь — MCP `media_status` и `media_open`. В изолированном коворке
   они используют UID-коннектор, как и `/usr/local/bin/polza-media status`.
   Личность определяет текущий системный пользователь; `--actor` не нужен.
   Это один механизм проверки прав, а не обход отказа через другой аккаунт.
   Не меняй роль и не читай закрытые конфигурации. При отказе зафиксируй его;
   при сообщении о восстановлении повторно проверь штатный MCP-инструмент.
3. Через MCP вызвать media_open, затем media_snapshot. Все 18 маршрутов описаны
   в MEDIA-ACCESS-PLAN.md; 17 браузерных профилей плюс отдельный Telegram-бот.
   Для формы входа вызвать media_login: пароль подставляет сервер из закрытого
   реестра, его нельзя включать в планы, печатать или просить у пользователя повторно.
   Снимок возвращает текущий URL, текст и реальные селекторы элементов.
   Проверяй, что открыт именно кабинет/редактор нужного аккаунта. HTTP 200
   или отсутствие пароля на странице не доказывают выполненный вход.
4. По снимку собери файл плана в проекте. Не выдумывай селекторы и результаты.
   Разрешены goto, fill, click, select, press, upload, expect. Нет evaluate и
   произвольного JavaScript. Нативный contenteditable поддерживается через fill.
   Если редактор или iframe требует неподдерживаемого действия, зафиксируй
   конкретный блокер вместо имитации готовности.
5. Изображения положи в каталог проекта. Файлы PNG/JPEG/WebP/GIF/PDF/DOCX до
   15 МБ передаются через upload. Не загружай исходные скрины с паролями,
   личными адресами или клиентскими данными без разрешения на эту публикацию.
6. Перед финальным click проверь уникальность текста, обязательные поля,
   иллюстрации и намерение пользователя. План должен закончиться expect
   с реальным текстом результата: подтверждением сохранения/отправки,
   статусом или видимым материалом, а не собственной строкой из тела статьи.
7. `polza-media job <путь-к-плану.json>` вернёт ID. Проверь его командой
   `polza-media job-status <ID>`. idempotencyKey — стабильный ключ материала,
   площадки и версии. Повторная отправка того же ключа не создаёт дубль.
8. waiting_for_human означает: вернуть пользователю handoffUrl на ту же VPS-сессию.
   После прохождения капчи и возвращения пользователя в чат вызвать media_resume;
   инструмент проверит исчезновение капчи и продолжит с невыполненного шага.
   needs_review означает: открыть snapshot и проверить, что успело выполниться.
   Не повторяй публикацию слепо новым ключом. После перехвата человеком или
   перезапуска автоматического повтора нет. completed означает успешные шаги
   и видимый контрольный текст; отдельно подтверди статус материала площадки.
9. Верни пользователю короткий отчёт: материал → площадка → ссылка → фактический
   статус. Если есть блокер — точное действие пользователя, которое его снимет.

Пример структуры плана, который составляет агент по актуальному snapshot:

```json
{
  "site": "workspace",
  "intent": "draft",
  "title": "Название конкретного материала",
  "idempotencyKey": "material-workspace-draft-v1",
  "steps": [
    { "type": "goto", "url": "https://workspace.ru/personal/cases/add/" },
    { "type": "fill", "selector": "СЕЛЕКТОР_ИЗ_СНИМКА", "value": "Проверенный текст" },
    { "type": "upload", "selector": "СЕЛЕКТОР_ЗАГРУЗКИ", "path": "/home/manager/work/polza-seo-pr/media-desk/cover.jpg" },
    { "type": "click", "selector": "СЕЛЕКТОР_СОХРАНЕНИЯ" },
    { "type": "expect", "text": "РЕАЛЬНОЕ_ПОДТВЕРЖДЕНИЕ_СОХРАНЕНИЯ" }
  ]
}
```

Это схема, не готовый адаптер Workspace. Реальные селекторы и контрольный текст
нужно получить из открытого редактора. Пароли не передаются в планах; они
подставляются media_login. Капчу, код и новые согласия подтверждает человек.

## Что уже работает и что зависит от root

Сервис запущен на VPS и использует текущую авторизацию коворка. Владелец и
`marker` имеют доступ к медиа; cfo и анонимные запросы его не получают.
Постоянный профиль Workspace проверен: открыт личный кабинет Polza с 99
опубликованными кейсами. Авторизация остальных площадок проверяется при открытии;
не объявляй все профили авторизованными заранее.

Сейчас одновременно открыт максимум один браузер из-за лимита потоков manager.
Наличие браузерного API не снимает блокер штатного запуска новых ограниченных
агентских чатов: коворку нужен Bubblewrap. Команды для Сергея находятся в
MEDIA-BROWSER-SERGEY.md и `/home/manager/services/polza-media-browser/setup-root.sh`.
Владелец может использовать инструмент из работающего агентского чата уже сейчас;
для новых чатов `marker` сначала нужна успешная проверка песочницы после установки.

Ключи не копировать в проект, сообщения или отчёты. Они хранятся в закрытой
конфигурации оператора, истекают через 30 дней и проверяют текущие права пользователя.
